# Local page checkpoint (experimental)

A policy-mode CLI crawl uses the same crawler as standard mode, but atomically saves each frontier page with a local evidence record. The record is keyed by the exact request ID and frontier URL; its capture normally repeats that URL and contains version 1 collectors for HTML occurrences, the link graph and resources. Current crawls also record robots provenance, HTTP occurrences and effective indexing decisions. Each has `observed`, `partial`, or `unavailable` state and an explanation for partial or unavailable data. HTML decoding errors and graph extraction limits, including truncated link names, are partial. Robots-blocked or failed responses and non-HTML responses are unavailable for the affected collectors. Resource bytes are decoded response bytes, not measured transfer bytes. The HTTP collector retains bounded occurrences before ordinary headers are combined. Earlier records can lack these collectors. The soft-404 collector records the S06 per-page assessment. Sitemap evidence is stored separately as a per-run discovery checkpoint, described below. See [local robots and indexing evidence](../local-robots-checkpoint.md). This is not an S02/S03/S05/S06/S08 completion claim or a delivery schema.

Each serialized collector is capped at 24 KiB; an oversized collector is replaced with an explicit unavailable marker. The 16 MiB observation threshold is not a hard storage cap: subsequent pages receive constant-size run-limit markers, which also consume space. A transactionally maintained per-run counter tracks evidence bytes; an older database initializes the counter from its existing records once, without rewriting them. Marker rows omit the redundant URL copy and retain its digest; the full URL remains the row key. The existing request limits allow at most 40,000 fetched pages and resources; the exact URL remains the SQLite row key. When its UTF-8 representation exceeds 8 KiB, the redundant URL copy in the capture is omitted with an explicit reason and SHA-256 digest. Page storage itself remains governed by existing crawler limits. The input hash records the bounded capture used for replay comparison, including when the stored capture was replaced by a run-limit marker. It does not assert the identity of data omitted by a collector. Existing local evidence and counters are retained indefinitely; no automatic retention or pruning policy is introduced. The budget covers evidence JSON bytes only, not URLs, pages, SQLite indexes, temporary memory or database overhead.

The checkpoint requires the exact claimed local request and a local-running job and existing frontier URL. The transaction checks page and capture identity and, on first write, matches page depth, sitemap membership and resource classification to the frontier. It rejects different replays and commits page, evidence and byte accounting together. Cancellation or finalization before the transaction rejects the write; if the transaction commits first, cancellation retains that checkpoint. Recovery retains local checkpoints and quarantines interrupted local runs as local-only; it does not resume them. Existing pages without records remain missing evidence, not empty evidence. Existing reports and outbox bytes are not rewritten, and local records are never queued for delivery. A cancellation or other state transition that wins before local finalization makes finalization return an error instead of reporting success. This local database format is not registered as a wire producer contract.

The HTML occurrence extractor may produce a partial result larger than the checkpoint's 24 KiB per-collector cap; in that case the entire collector is explicitly unavailable rather than retaining a prefix with revised omission counts. Replay compares the original bounded capture hash and page bytes, including for run-limit markers, but does not audit database corruption by recomputing hashes of retained captures. These are experimental local storage limits, not assurances about omitted source data.

## Offline CLI acceptance fixture

A build explicitly compiled with `--features local-cli-fixtures` accepts `SEOSMITH_LOCAL_FIXTURES` for a policy-mode local CLI crawl. The variable names a JSON object mapping exact URLs to `{ "status": 200, "headers": {"content-type": "text/html"}, "body": "..." }` responses. For repeated fields, supply `header_fields` as a list of name/value pairs, including the content type. When present, this list supplies all headers and takes precedence over the map. This test-only transport reads at most 1 MiB from the fixture file and never falls back to networking for a missing URL. The feature is disabled in default builds; it does not change the standard crawler or its address checks.

`tests/local_cli_fixture.rs` starts that CLI as a separate process with a synthetic robots file, sitemap response and HTML, then opens the upgraded store. It checks page and collector records, local-only finalization, legacy report bytes, stored hashes, delivery states and the pending queue. No hosted service is needed.

The local `soft_404` collector uses the versioned S06 per-page detector on the fetched response bytes, status and content type. A successful candidate or no-candidate assessment is observed; unknown with extracted evidence is partial, and unknown without evidence is unavailable. Both retain the versioned decision and detector reason unless a collector or run limit replaces the data. Its candidate is a signal, not a provider indexing determination; unknown and unavailable sources remain explicit. No peer comparison or additional requests are made. Collector and run byte limits apply as for other local evidence; old captures are not rewritten.

## Local sitemap discovery checkpoint

A policy-mode local crawl stores version 1 JSON in `local_sitemap_run`, keyed by request ID. It uses only response bytes the normal discovery already fetched, and does not feed its parser back into discovery. Roots are capped at 32 and source events at 64; copied URLs are capped at 2 KiB. Omitted root and source counts and the count of invalid or out-of-scope robots directives skipped by discovery are explicit. Each fetched document uses the reviewed parser with a 256 KiB input and expanded-body bound, at most 256 retained entries and a 16 KiB serialized document budget. A document's error and `omitted_entries` distinguish exact omissions from unknown counts. Source events identify robots and duplicate skips, the crawler's source limit, pending/unknown fetches, HTTP failures and transport failures. A source URL or document that cannot fit is represented by an omission count or an explicit unknown marker. Index documents retain the original entry ordinals, so `sitemap_evidence::entry_origins` can reconstruct duplicate and nested paths without inventing parent ordinals. An absent or truncated document makes traversal partial.

The run `discovery_state` describes the crawler outcome separately from `state`, which is partial when coverage is bounded, a source is unavailable, or a retained entry is invalid or outside scope. `remaining_sources_unknown` marks an interrupted or source-limited traversal. An initial in-progress record is committed before robots collection; the completed or timed-out snapshot is committed atomically while the job is local-running, serialized with cancellation and finalization. Fetched 200 bodies also have a SHA-256 digest, including bytes omitted from retained entries. Equal snapshots may be replayed; different terminal snapshots are rejected. An interrupted run can therefore retain the initial unknown marker rather than a partial snapshot. Existing jobs have no row and must be treated as unknown. The per-run record is separate from page collector budgets and is not sent in a report or delivery. It is bounded by 2 MiB of JSON, excluding SQLite overhead. This does not claim S03 or provider coverage.
